nictiz-ui {{ .Chart.AppVersion }} deployed as release {{ .Release.Name }} in namespace {{ .Release.Namespace }}.

  URL:   http{{ if .Values.ingress.tls.enabled }}s{{ end }}://{{ .Values.ingress.host }}
  Image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

Before it works, check these in order:

1) DNS — {{ .Values.ingress.host }} must resolve to the hcloud load balancer IP:
     terraform -chdir=<stack>/terraform/envs/hetzner output load_balancer_ipv4

2) The health-stack release's Keycloak admin Secret must exist here — the
   registration Job authenticates with it:

     kubectl get secret {{ .Values.keycloak.registration.adminSecret }} -n {{ .Release.Namespace }}

3) The registration Job must have succeeded — it creates/updates this app's
   OIDC clients (+ demo user) in the {{ .Values.keycloak.realm }} realm on every
   install and upgrade:

     kubectl get job {{ include "nictiz-ui.fullname" . }}-register-clients -n {{ .Release.Namespace }}
     kubectl logs job/{{ include "nictiz-ui.fullname" . }}-register-clients -n {{ .Release.Namespace }}

   (On a fresh full-stack install it retries until Keycloak is up — a few
   minutes of restarts is normal.)

{{ if .Values.auth.oauth2Proxy.enabled -}}
4) oidc.issuerUrl ({{ .Values.oidc.issuerUrl }}) must be the {{ .Values.keycloak.realm }} realm's
   PUBLIC issuer on the health-stack host. The oauth2-proxy pod fetches OIDC
   discovery from it through the LB at startup, so it cannot go ready until
   Keycloak + DNS + TLS are up — a crash-looping proxy pod right after a fresh
   install is normal for a few minutes.
{{- else -}}
4) ⚠ THE BROWSER LOGIN IS DISABLED (auth.oauth2Proxy.enabled=false).
   Nothing gates this host. The BFF applies no per-user access control, so
   anyone who reaches {{ .Values.ingress.host }} can read and write EVERY record
   in the CDR.
{{- if .Values.auth.required }}
   auth.required is still true, so the BFF will 401 everything — the app will be
   unreachable rather than exposed. That is the intended failure direction, but
   it does mean this configuration is not usable as-is.
{{- end }}
{{- end }}

5) Watch it come up:

     kubectl rollout status deploy/{{ include "nictiz-ui.fullname" . }} -n {{ .Release.Namespace }}
     kubectl logs -n {{ .Release.Namespace }} -l app.kubernetes.io/name={{ include "nictiz-ui.name" . }} -f

6) Verify end-to-end:

     curl -s -o /dev/null -w '%{http_code}\n' https://{{ .Values.ingress.host }}/api/health   # 302 → login
     TOKEN=$(curl -sX POST <issuer>/protocol/openid-connect/token \
       -d grant_type=client_credentials -d client_id=api-client \
       -d client_secret=<terraform output kc_api_client_secret> | jq -r .access_token)
     curl -H "Authorization: Bearer $TOKEN" https://{{ .Values.ingress.host }}/api/health     # 200

   /api/health reports whether the BFF can reach EHRbase and HAPI — that is the
   check that tells you the releases are actually wired together.
{{- if .Values.keycloak.demoUser.enabled }}

   Browser login: user "{{ .Values.keycloak.demoUser.username }}", password from

     kubectl get secret {{ .Values.keycloak.demoUser.secretName }} -n {{ .Release.Namespace }} -o jsonpath='{.data.password}' | base64 -d
{{- end }}

{{- if .Values.auth.required }}

NOTE: REQUIRE_AUTH is on, so the BFF rejects any request without a proxy
identity. A direct `kubectl port-forward` to the Service will therefore 401 —
that is deliberate, not a bug.

The reliable way to test is THROUGH the ingress, which is what supplies that
identity. Over a port-forward you must forge the header the BFF reads:

    curl -H 'X-Auth-Request-User: tester' http://localhost:3001/api/health

(That this forgery works at all from inside the cluster is exactly why the
NetworkPolicy exists.)
{{- end }}
